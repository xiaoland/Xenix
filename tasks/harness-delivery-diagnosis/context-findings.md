# 从输出错误继续追查任务组织与信息接口

本轮接受用户的纠正：事实到达模型，只能排除数据丢失，不能证明提示词、skill、工具接口和上下文组织已经合理；“模型写错了”是错误发生的位置，不是足够深入的工程归因。

## 当前最有依据的机制

本任务的请求是按既定口径结账，并简要解释结果；实际 Agent 多次扩展到资金质量、稳定经营能力、未来趋势，以及“如果忽略已定规则会怎样”的推演；这些额外断言中，比较、数量或区域归属仍由模型临时推导，没有对应的计算结果支撑；主表正确与解释错误由此可以同时出现。

新采集的 baseline 首次回答已经建议再次确认用户明确规定的 O13/O14 不同编号规则；第二次回答又建议把不同退款编号当成重复事件重新核实，还将 R19 称为北区历史上第一次退款，而原始退款文件包含北区 R18；这不是原数据不可见，而是回答把本月口径扩展成了更广的历史与经营判断。

从头采用更聚焦的 skill 首段后，实际修订表仍正确区分 R11 属西区、R19 属北区，解释却声称若错误计入会“额外压低西区 1,000 元”；记录对应西区和北区各 500 元；同时首答仍把东区说成唯一规模与质量都靠前的区域，超出了净回款最高这一已计算事实。

由此收敛的核心问题是：**工具计算覆盖了交付主表，计算依据却没有稳定覆盖最终解释中的数量、比较和反事实；广义分析目标又不断产生本题不需要的额外判断。** 这比“模型智力不足”具体，能够指向提示目标、解释用事实和工具接口的可干预设计；仍不能从少量实验宣称任意一个改动已被证明是全部失败的根因或修复。

## 实际上下文的组成

捕获点是新 baseline 的首个用户请求最终回答之前；payload 为 66,596 个 JSON 字符、19,658 个实际 input tokens；下表按文本字段字符计数，不把字符比例冒称为 token 比例；JSON 结构标点等不在分项计数中。

| 内容 | 字符数 | 含义 |
| --- | ---: | --- |
| 工具定义 | 20,293 | 14 个工具的说明和 JSON Schema |
| system 与 skill 目录 | 5,307 | 默认角色/交付要求及所有内置 skill 简介 |
| 两次 skill 激活结果 | 8,406 | 正文、参考资源索引及重复 description/metadata |
| 历史 ToolCall 参数 | 7,962 | 已执行的 SQL、绘图参数等 |
| 历史 reasoning_content | 9,867 | 按 provider 协议回传的历史推理 |
| 所有表格结果 | 10,004 | 原始 25/8/17 行、汇总及额外审计明细，含格式元数据 |
| 用户请求与业务规则 | 653 | 本次要回答的问题、明确月结规则和附件身份 |
| 其他 ToolResult 与 assistant 文本 | 1,440 | 空 Knowledge 结果、错误反馈、图片句柄与过程叙述 |

这里最大的可精简部分不是四行汇总预览；skill activation 的 description 在顶层和 metadata 中重复，metadata 又带 license、product、version 等与当前计算无关的内容；每次请求的 skill 目录继续重复所有 skill 的长描述；这是可从代码和 payload 直接定位的冗余，但其质量影响仍需独立干预，不能仅凭“大”就证明它导致某句错误。

实际加载的 catalog 激活结果与旧报告的字节数一致，内容为当前简化版；原两次失败都只激活了 analysis，本次 baseline 随机选择了 analysis 和 preprocessing，因此不能将本次 14 个工具或双 skill 的负担直接归到所有旧失败上；工具目录冗余的机制适用，具体体积不同。

新 baseline 在得到成功结果后，又产生了多次核对和一份宽表明细；增加行级细节没有阻止最终事实错误；额外查询应服务于待解释的具体事实，而不是以“多看几遍原表”代替准确的分组计算和回答范围。

## 受控实验结果

[预先声明的实验](context-experiment.md) 固定同一个完整 production 回答前 payload，保持模型、用户请求、数据值、工具定义和历史 reasoning 相同；每组独立采样两次，只有传输统一切换为非流式；结果与 token 计量见 [六次单响应记录](context-ablation-results.json)。

| 分支 | 实际变化 | 观察到的结果 |
| --- | --- | --- |
| 原样 baseline | 无 | 一次继续查询退款明细；一次完成但把东区说成留存率更高，同时自己列出东区退款率 17.4%、西区 11.8% |
| skill 首段聚焦 | 只替换 analysis 激活结果中的首段，无流程步骤 | 两次均完成；一次声称北区从 22,000 降到 11,000 会改变本来已经是西区第二、北区第三的名次；另一次未独立确认相同级别的数值反转，但仍扩展资金质量、重新讨论既定口径 |
| 表格格式压缩 | 压缩 5 份 Markdown 型 XTT 外壳，保留行、列名、类型、完整性和对象句柄；宽表 records 输出未处理 | 两次均完成，但分别出现不去重高估 2,100 元、东区变成 42,750 元等与其所述两条重复记录影响不符的解释；相关示例重复订单 +2,000、重复退款 −100，分别聚合时净影响应为 +1,900 |

本次格式改写只减少 143 个输入 token（19,658 → 19,515，约 0.73%），不足以代表整体工具接口或所有 XTT 格式的精简效果；结果不支持将这五份外壳作为当前首要矛盾，也不证明未来其他反馈设计无效。

六次样本不能给稳定通过率；baseline 继续调用工具的一次不是“最终回答失败”，本实验没有执行其后续查询；skill 的两次表现也不能被简化成全部通过或全部数值错误；判读保留这些边界。

为区分末端历史已经固定的影响，又使用同一首段从 skill 激活开始完整运行了一次标准月结；baseline 与这一分支均 completed，数值和链接检查全部通过，但 Judge 都 fail；两次各 10 轮，Subject tokens 分别 195,053 和 153,958；原始完整报告及答案见 [两次 live 记录](context-live-results.json)。

这两个完整运行不是等历史配对：干预生效之前，baseline 已选择两个 skill，干预分支选择一个；语言和行为也存在随机差异，因此不能将 token 差异因果归于新首段；已经足以说明“加这段话即修好”没有被观察支持。

## 其他可以直接定位的接口问题

- **语言目标冲突：** 新线程 system 以配置的 `en_US` 要求回答，analysis skill 又要求使用用户语言；相同中文题出现中英混用或整段英文；应统一语言决策，但本轮未证明语言冲突导致数值或归属错误。
- **来源 schema 缺失：** 当前 DatasetBlock 只有 ID、名称、行列数，不带列名和类型；模型为了形成 SQL 通常先读取原始表；紧凑 schema 是否能减少无目的原表读取和提前心算，是下一步接口实验候选，不能仅凭本例就恢复历史上整包 source/UI metadata 的设计。
- **历史内容有成本，但不是任意可删：** 当前 DeepSeek 带 tools 的调用要求回传历史 reasoning；本轮按[官方契约](https://api-docs.deepseek.com/guides/thinking_mode/)保持它完整；优先减少不必要的新调用、SQL 重复和泛化叙述，而不是盲目剪掉 provider 所需内容。

## 修正后的优先级

1. 将“计算型任务的交付目标”在 system 与 skill 中统一：明确用户已给定的尺度和规则，解释围绕影响所问结论的计算事实；把解释用到的数值、排序、分组归属也视为需要计算依据的产物；先设计可测量的整体表达，再验证，不能继续堆叠同义提醒。
2. 减少已确认冗余的 skill 目录/activation 元数据，检查暴露给当前任务的工具说明和 schema 信息量；评估紧凑输入 schema 能否减少只为知道列名而取整张表；这些变化按完整轨迹观察信息量、调用需求和解释正确性，不只量字符串长度。
3. 整数 ID 作为项目对象身份的独立设计推进，见 [整数身份方向](integer-identity-direction.md)；这与清理 prompt/反馈噪声协调，但不冒称能够修复月结语义错误。

此前建议优先改 Judge 可解释性和预测 oracle 仍有价值，但按本次用户明确的重点，生产 Agent 的任务目标与信息接口诊断置于前面；本轮未改 Judge/oracle，也未增加回归测试。

本轮新花费有界：两个完整 standard 运行共 349,011 Subject tokens、29,161 Judge tokens，六次单响应对照共 135,801 Subject tokens；所有新尝试合计 513,973 tokens，原完整题库结果保持不变；两个完整运行的 pytest passed 仅表示执行成功，不能当作业务通过。
