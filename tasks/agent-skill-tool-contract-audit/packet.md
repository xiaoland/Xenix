# Agent Skill Tool Contract Audit

## Objective & Hypothesis

Audit current Xenix Agent skills for mismatches between skill instructions/assets and the actual Xenix tool contracts.

Current hypothesis: the word-cloud failure in thread `2518555a50c1450ba6ac963a69b12e21` was caused by stale `xenix-data-analysis` knowledge. The skill's Vega word-cloud asset uses a data-level transform pattern, while `analysis.graph` accepts Xenix-injected data and only permits layout transforms at the mark level.

  - `xenix-data-preprocessing`: cleaning, integration, transformation, role binding.
  - `xenix-data-modeling`: model metadata, training, tuning, apply, interpretation.

## Findings

### Confirmed: `xenix-data-analysis` word-cloud template mismatches `analysis.graph`

`assets/vega/wordcloud.vg.json` uses `data[].transform`, and `visualization-vega.md` tells the agent to replace `data.values`. `analysis.graph` drops user-provided Vega data declarations and injects the registered dataset. Its validator rejects transform nodes outside Vega mark objects.

Impact: the LLM concludes the environment does not support wordcloud, even though the service does support a narrower mark-level wordcloud profile.

Runtime reproduction with a synthetic `word,frequency` CSV:

- `assets/vega/wordcloud.vg.json` fails with unknown generated fields: `angle`, `font`, `fontSize`, `fontWeight`, `x`, `y`.
- Cause: those fields are generated by the asset's data-level transform, which `analysis.graph` removes before rendering.

Status: fixed. The word-cloud asset now uses Xenix-injected `xenix_data` and puts the `wordcloud` transform directly on the text mark. `visualization-vega.md` now states that `from.transform` and top-level Vega `data` are not supported for this path.

### Confirmed Wording Risk: other Vega assets still say `Replace data.values`

The following assets render with synthetic CSVs, but their descriptions still instruct the agent to replace `data.values`:

- `assets/vega/topn-bar.vg.json`
- `assets/vega/time-line.vg.json`
- `assets/vega/heatmap.vg.json`

`analysis.graph` ignores user-provided Vega `data` declarations and patches mark/scale data references to the injected dataset. These assets happen to work when the registered dataset already has the expected fields, but the instructions teach the wrong mechanism.

Impact: lower than wordcloud, but it can make the agent spend effort editing `data.values` that the tool will discard. Data preparation should be described as `data.transform` producing a registered dataset with expected fields, not editing Vega inline values.

Status: fixed. Bar, line, and heatmap assets no longer contain inline `data.values`; the reference now tells the agent to prepare a registered chart-ready dataset and let Xenix inject it.

### Confirmed: `data.integrate` skill text overstates the tool

`xenix-data-preprocessing/references/preprocessing-tools.md` describes `data.integrate` as if it plans joins:

- join keys;
- uniqueness;
- expected join type;
- duplicate-key risk;
- column conflicts.

Current `data.integrate` tool schema only accepts:

- `dataset_ids`
- `name`

Current implementation concatenates loaded frames with `pd.concat(..., ignore_index=True)`. It does not accept join keys, join type, or conflict policy.

Impact: the agent may call `data.integrate` for a horizontal join and get a vertically stacked dataset. For SQL joins and reshaping, the correct tool is `data.transform` with multi-input `bindings`.

Status: fixed. `data.integrate` is documented as vertical append only. Horizontal joins, feature construction, reshaping, and grain changes are routed to `data.transform` with bindings.

### Confirmed Wording Risk: SQL recipes use `{{table}}` without naming the tool alias contract

`duckdb-sql-recipes.md`, `association-analysis.md`, and `data-quality-checks.md` use `FROM {{table}}`. `duckdb-sql-recipes.md` says placeholders should be replaced with names from `data.peek`.

Actual tool contract:

- single input through `dataset_id` is available in SQL as alias `input`;
- multi-input SQL uses explicit `bindings[].alias`;
- `data.peek` does not provide a SQL table name.

Impact: an LLM may replace `{{table}}` with a dataset name or file-derived table name and produce a failing SQL query. The docs should state: use `input` for single-dataset calls, and use the provided binding alias for multi-dataset calls.

Status: fixed. Single-dataset SQL templates now use `input` directly, and the alias contract is stated in the SQL recipe, association analysis, and preprocessing quality-check references.

### Confirmed: modeling presets contain non-tool parameter fields

`xenix-data-modeling/references/model-presets.md` and `assets/model-presets.json` contain conceptual fields that are not accepted by current model parameter schemas:

- split policy fields such as `split`, `test_size`, `stratify`, `random_seed`;
- preprocessing policy fields such as `preprocessing.numeric`, `categorical`, and `missing`;
- requested output fields such as `metrics`;
- logistic regression fields such as `penalty`, `class_weight`, and `random_seed`;
- classification random forest `min_samples_leaf`, which is not in current `classification.random_forest` schema;
- MLP fields `hidden_layer_sizes` and `early_stopping`; current schemas use `hidden_layer_size` and do not expose `early_stopping`.

Current model tool contract:

- `model.train` accepts `models: string[]` and `params_by_model: object`;
- `model.hyper_train` accepts `param_grids_by_model: object`;
- canonical parameter schemas are exposed by `model.metadata(include_param_schema=true, include_param_grid_schema=true)`;
- Pydantic model validation may ignore extra fields, which is worse than a hard failure because the agent can think a parameter was applied when it was not.

Impact: high for modeling quality. The skill says the presets are conceptual and should be adapted, but the JSON asset is structured enough that the LLM may copy it into tool calls. The asset should be reshaped to canonical `model_key` and valid `params` / `grid` fields, or downgraded to prose-only guidance that always tells the agent to call `model.metadata` first.

Status: fixed. Modeling presets now use canonical `model.train` / `model.hyper_train` shapes and parameters accepted by the current schemas. MLP guidance now uses `hidden_layer_size`, and the docs route exact schema authority to `model.metadata`.
