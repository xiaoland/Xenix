# Harness benchmark 第二批：业务决策与任务族

- **基线**：首批提交 `974db27`（`refactor: 按完整业务任务重构 Harness benchmark`），提交后工作区干净。
- **当前授权与状态**：2026-09-13 用户批准开始第二批实现，现已完成并获准整理提交。补货家族、两个回访对照、月结 Judge 事实与校准材料已落地；41 项基础验证通过，七个真实任务中六个 Judge pass、一个解释错误 fail，月结校准 12/12 匹配；未修改生产服务或 Skills。详见 [实施记录](implementation.md)。
- **推荐**：第二批集中做两件事：① 按关键业务判断组织可解释的对照任务族；② 用“预算约束下的补货决策”新增多种合法方案和有依据的不下单终态。把两者合为一个落地切片，先证明一个新任务族成立，再推广。
- **配套而非主线**：用首批真实交付做少量 Judge 校准，明确关键错误与缺少解释的区别。Harness 收束、ML 分组冲突和错误信息不足仍是产品发现，不自动变成第二批 benchmark 的主目标。

## 为什么选这两项

首批已完成从能力演示到完整业务工作的迁移，也支持多轮、等价交付与确认变化。下一批的增益来自覆盖新的业务判断，而不是继续复制三道题、增加工具调用要求或堆叠验证字段。

| 高价值改进 | 当前证据与具体代价 | 第二批改变 | 最小落地 |
| --- | --- | --- | --- |
| 按业务判断组织对照任务族 | A/B 有精确金额/名单真值；confirmation 同时改变多个业务条件。它能检验整体迁移，但一次失败未必解释是哪项判断没有迁移；首批确认数据也已参与开发观察。 | 每个家族记录业务目标、关键判断、允许终态，以及改变一个业务条件后的预期影响；同时保留独立场景做确认。展示差异，不把变体数量当覆盖权重。 | 先为补货建立普通、预算改变、到货改变、无可采购批次等场景；对回访只补最有价值的单条件变化。使用已有 pytest 选择与报告，不建设第二套注册器。 |
| 评价多种合理业务方案 | 首批 C 已允许不同算法和达到门槛的预测，不能说所有题都只有一个答案；但三项核心的业务终点都预设为交付可用表/名单/分析器。尚无多个同等优秀行动方案、或完成分析后合理不采取行动的任务。 | 用公开目标与约束定义成功，接受满足目标的所有方案；不下单是否正确取决于业务条件，不能一概算失败，也不能奖励泛泛的谨慎。 | 新建“有限预算与仓容下的补货”任务族：验收采购计划是否可行、目标值与解释，不要求某份参考 SKU 清单或指定算法。 |

这两项分别改善“题库怎样组织和解释”与“题库衡量什么”。小型探针已经证明它们能够落在同一个具体任务上，详见 [候选设计](candidate-design.md) 与 [实验结果](experiments/observations.json)。

## 学习 FrontierHarness 的具体取舍

本轮复核固定版本 `8f11b130c30bbf76ca1f3edeea70abc773bd8d2c` 的 [约束排期题面](https://github.com/frontier-harness-eval/eval/blob/8f11b130c30bbf76ca1f3edeea70abc773bd8d2c/tasks/constraints-scheduling/instruction.md)：硬约束、优选目标与仅供参考的偏好具有不同作用。Xenix 借鉴的是把这些角色讲清楚，再验收实际方案；本地补货设计是据此形成的推演。该来源自身要求最早可行时点，不是“任意方案均可”的证据。

[多源合并题面](https://github.com/frontier-harness-eval/eval/blob/8f11b130c30bbf76ca1f3edeea70abc773bd8d2c/tasks/multi-source-data-merger/instruction.md) 明确给出来源优先级，冲突因此具有确定解。这提示我们区分“能够按业务规则解决的差异”与“确实缺少业务权威信息”的不同任务；不能把前者每次都改成向用户询问。成对变化、允许不下单与任务族组织是本项目的设计决定，未声称该仓库已有相同机制；本轮没有审计其 verifier 或学习其执行架构。

## 顺序与暂缓项

| 优先级 | 内容 | 取舍 |
| --- | --- | --- |
| 本批主切片 | 补货决策任务族 + 可归因的业务变化 | 同时证明新的业务覆盖、多解验收与任务组织；可独立于当前 ML 缺陷推进。 |
| 同步小项 | 月结 Judge 的正确/等价、解释缺失、实质错误校准材料 | 已有真实证据，可直接改善分数含义；复用现有校准入口，不先扩建 Judge 平台。 |
| 后续候选 | 是否采用已有分析器；证据充分与不足的成对任务 | 产品价值高，但要定义足够支持或否定采用的可核对证据；不能从一个低分或合成生成器直接推断“数据不可学”，也不能偷改现有 C 的 90% 交付目标。 |
| 后续候选 | 有实质影响的口径缺失 → 澄清 → 继续交付 | 长期重要；当前 runner 只支持预定请求序列，尚无按实际提问选择业务回应的能力。应先设计有限且公平的回应材料；不为凑一题先建用户模拟器。 |
| 后续候选 | 无标签客户理解、面向未来的方案选择 | 需要多解业务价值或预测质量的可信判据。旧聚类题锁定分区，旧预测题侧重模型产物与评估；不能把它们搬回核心就声称补齐了决策能力。 |
| 独立产品工作 | Harness 工作收束、ML 分组策略与训练错误投影 | 首批已有具体缺陷证据；先保留失败，生产修复需要该目标的授权。它们不决定第二批题库的方向。 |

没有真实用户频率与损失数据，以上是依据 [PRD](../../docs/10-prd/README.md)、当前实现和首批观察作出的优先级判断，不是定量 ROI 排名。
