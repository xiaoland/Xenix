# 候选设计：有限资源下的业务决策

历史设计：本文保留实施前的题面原型和 From → To。2026-09-13 用户已批准开始，实际正式数据与实现见 [实施记录](implementation.md)；下文原型中的金额、商品与状态不是当前正式 benchmark。

## 用户要完成的工作

题面原型：“请根据供应商本周可订的批次，制定一份本周补货计划。预算上限 300 元，新增货物最多占 10 箱仓容，必须在 5 天内到货。每个报价批次最多采购一次，批次不能拆分。按已确认的预计增量毛利，选择使本周预计增量毛利最高的组合；同样好的方案任选其一，不必为了用完预算多买。交付可下载的采购计划，并说明为什么这样选、用了多少预算和仓容。如本周没有可采购的批次，请明确给出不下单结论及具体原因。”

金额较小是推演用途，不是正式业务规模。正式题面保持目标、资源条件和交付，不给枚举、SQL、模型、工具或先后顺序。预计增量毛利在本任务中是业务方已确认的计划参数；本题评价给定参数下的决策，不暗中要求预测未知未来需求，也不把计划毛利解释成实际兑现收益。

## 原型与已观察结果

原型有 8 个不可拆采购批次，分别包含采购成本、预计增量毛利、箱数、到货天数；各批次收益独立，没有未说明的组合折扣或需求重叠。完整数据由 [探针脚本](experiments/probe_decisions.py) 拥有，也保留在 [observations.json](experiments/observations.json)。

| 场景 | 相对普通场景的唯一业务变化 | 最优可行结果 | 能区分的判断 |
| --- | --- | --- | --- |
| 普通 | 无 | A+C 或 B+C；成本 260，仓容 10，预计增量毛利 370 | 两份不同 SKU 组合都应通过；只选单项毛利最大的 H 虽可行，但只有 320，不是最优。 |
| 预算变化 | 预算从 300 降至 240 | A+D 或 B+D；预计增量毛利 325 | 沿用旧组合会超预算；不是改名字后继续背答案。 |
| 毛利变化，改变行动 | C 的预计毛利从 130 降至 60 | A+D+F 或 B+D+F；预计增量毛利 353 | 偏好来自业务收益；小批次也可能有价值，不能仅按单项收益贪心。 |
| 毛利变化，保持行动 | C 的预计毛利从 130 升至 140 | A+C 或 B+C；预计增量毛利 380 | 数据值改变不代表行动一定改变；解释与合计须更新。 |
| 到货变化 | G 的到货时间从 8 天变为 3 天 | A+G 或 B+G；预计增量毛利 470 | 业务可行性条件有独立作用；不能把此前不适用的选项永久排除。 |
| 本周不下单 | 预算从 300 降至 20 | 空采购计划，预计增量毛利 0 | 最低可采购批次成本为 30，不下单是具体业务结论；普通场景下相同空计划不成立。 |

行序变化与统一改编号保留选择含义。枚举复核还纠正了原先对“C 毛利降低”的手算：漏掉 F 会使方案停在次优，正确最优值为 353。这说明作者答案也需要独立核对，不能把第一个想到的参考清单当真值。

这些场景只证明小型任务自洽、关键判断有可观察后果。未调用 Subject 或 Xenix 服务，不证明实际难度、代表性或 ML 能力。正式输入应另写独立业务目录，包含不同资源瓶颈、批次量与价值关系；不把 8 个二元选项、A/B 平手或这些数字固化为未来题目的永久结构。

## 成功由目标与约束决定

程序事实：采购身份与数量可读，满足本题给定的预算、容量、可采购量和到货条件；计算实际方案的成本、资源消耗与目标值，和作者侧独立求得的可达最优值比较。保留所有同等最优解，不与一份固定 SKU 清单做完全相等比较。额外审计列、行列顺序和明确的金额单位沿用首批的等价交付原则。

本原型公开目标是最高毛利，完整成功要求达到最优值；可行但次优的结果保留其收益与差距作为诊断，不能暗加“达到参考方案 95% 即通过”的隐藏容差。若未来正式业务允许近似方案，应先在业务要求中给出容许损失，再决定判据。

Judge 评价实际推荐方案和解释是否一致，是否正确说明主要约束、未用预算以及不下单原因。程序已经算出的预算和毛利不交给 Judge 凭印象重算；也不让句子“我已优化”代替合格方案。选 A+C 或 B+C 都正确；使用哪种搜索、分析或模型方法不构成评分点。

有依据的不下单同样要有完成的业务答复与可复核结果。预算不足场景中的空计划允许通过；普通场景中泛泛表达“不确定，建议人工再看”既没有完成最大化任务，也没有证明没有可行采购，不获得奖励。此变化不会修改当前工单分流题已明确要求保存、复用并达到 90% 的原契约。

## 任务组织改变

每个家族用简短记录表达“用户目标、关键判断、允许终态、关键变化及预期影响、独立确认材料”。它是题目作者的设计记录，可放在 fixture guide 和 case 中，不是新的通用类型系统。实例仍由 pytest 文件/参数与明确 selector 选择。

区分三种材料用途：普通实例用来开发；单条件变化用来定位业务判断是否迁移；另写的完整场景用来确认。综合确认一次改变多个条件仍有价值，但不能从它单独推断某项条件的因果作用。对照实例也不等同于统计因果识别；固定模型与资源后仍需考虑采样随机性。

第一批回访的八月变体同时改变消费门槛、回访间隔和城市，因此可以先添加一组最有价值的单条件变化；不需要所有条件的笛卡尔积。月结新增更多金额排列的边际价值较低，优先保持现有跨轮任务。工单先保留当前失败，另一个“是否值得采用”的任务必须拥有独立业务目标和证据，不能把失败的复用题改名后算成功。

报告按业务家族展示各场景结果及差异，重复与变体数不增加家族权重；初期无需加权总分。默认核心可以只取每个家族的代表任务，其余对照通过显式选择运行，避免每加一个设计变化就抬高全部日常运行成本。公开用于针对性修改的材料，不继续称作未见确认集。

解释不同场景的业务差异，不等于用现有 `compare` 将异质报告合成 Harness 改进趋势；模型或 Harness 的前后比较仍使用同一场景和评分口径。

## 建议下一步的 From → To

这是实施前提出并随后获得用户批准的范围；实际改动与验证另列在实施记录中。

| 维度 | 当前 | 建议第一切片 |
| --- | --- | --- |
| 核心覆盖 | 月结修订、回访资格、保存与复用分流器 | 新增约束补货决策家族，允许多个最优方案及有依据的空计划；其余三项保留。 |
| 变化组织 | 每题 standard / confirmation；变化含义主要在说明文档 | 为新家族明确单条件变化与独立确认；回访仅补必要的判断对照，不全量组合。 |
| 完成判据 | 当前各题的金额/名单/复用与质量条件 | 新题按实际行动的可行性和目标值验收；不建立全库“每次必须行动”或“每次都要澄清”的通用规则。 |
| 交付与执行 | 已有多轮、交付冻结与 v6 结果 | 优先复用，不为本题引入规划器、用户模拟器、通用求解层或新报告大版本；选定实例能从 case 身份区分。 |
| Judge | 已有 rubric、事实输入与可选校准入口 | 对首批实质错误的严重程度做小量校准，再为新题给明确评分锚点。 |
| 验证 | 首批有离线探针与开发 live 记录 | 独立求值、合法多解/次优/不可行/合理不下单反例、相称 live 试跑；不先承诺通过率，不先提高预算。 |

拟涉及：新增业务 case 与其 `fixtures/business_tasks/` 材料，必要的 pytest 场景选择和 unit-tdd/贡献指南说明。现有 runner、预算、报告只有在任务实证出缺口时才改变；生产 Harness/ML 与 Skills 不属于此切片。正式数据与判据完成后再给出最终修改地址，避免现在为尚不存在的问题列出大范围实现清单。
