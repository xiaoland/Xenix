## 因果诊断

原始分流 trace 的 `benchmark.subject.outcome` 保留了真实 Tool 参数、结果状态、返回规模与每轮 Tool 分组。standard `3606366b03dc45e397d1119fa895fb0c` 在 1–7 轮依次激活、读取引用/概况、批量查询、继续查询、全文条件查询、模型元数据和角色绑定，第 8 轮才训练；随后比较四种参数、应用历史数据，再查历史准确率/置信度。训练均成功，超轮并非全由服务失败造成。系统提示的固定流程可能促成这些行为；未经对照，不能声称是唯一原因。

confirmation `ab16b65b247d423a8d2532ad4903777d` 的不分组 binding 训练失败，而显式分组 binding 训练成功。之后继续使用无 group 的 binding 并修改词频/短语参数，又产生同样失败。Tool 返回只包含通用 task failed，实际原因仍保存于任务记录；让 Agent 另查日志既增加成本，又没有修复策略来源冲突。

多语言文本模型始终构造模板/业务关联组；模型现在通过内部 `uses_automatic_groups` 声明该事实，MLService 据此创建分组评估快照。分组算法和现有验证不变，未在 worker 里偷偷改写请求策略，也未让 Agent 负责知道内部模板分组。

两个同步 wait 路径现在返回保存的 `error_summary`。训练/调参共用训练等待，应用共用任务等待；任务 id、状态和原始业务原因一并可见，没有新增日志扫描或错误分类层。

新 Thread 的默认系统提示去掉字段取舍前置说明、每项结论通用风险声明和最终过程追踪要求，改为按实际问题和已有证据交付，并说明训练返回的评估可以支持选择与误差估计。没有新设 Tool 顺序、步骤配额或完成裁判；旧 Thread 保留其持久化提示，没有 migration。

## 测量修正与结论边界

第一轮两项超轮报告中的输入保留检查都通过，但 `integrity.passed` 因整体 run_status 不是 completed 而被置为 false。这是汇总语义误报。现在完整性仅由实际完整性检查决定，执行失败和预算超限仍保持原状。41 项既有 benchmark 基础检查通过；[旧事实的新投影](integrity-reprojection.json) 单独保存，没有覆盖原报告，也没有将任务改判成功。

还验证了一个影响重复测量的既有因素：分组留出以完整 DatasetSnapshotFact 的摘要参与排序，其中含随机 dataset_id。相同内容与 random_state、只换导入 id，就可能产生不同留出组；因此前面少量重放的分数或轮数变化不能全部归因于提示。现将新分组监督训练升级为 `group_hash_holdout.v2`，按内容摘要排序；已有 v1 请求仍使用原算法，避免重算旧模型时改变证据，不需要 migration。[双版本探针](split-version-observations.json) 确认新策略不随导入 id 改变，旧策略仍复现修改前的两个不同划分。现有真实生命周期 oracle 同步采用新策略，没有新增回归测试。

新策略修改后再次运行现有 ML registry、执行、文本分类 engine/service，共 21 项通过；其中 engine 的显式 v1 请求仍通过真实训练与评估。`pdm run check` 通过。[最终服务探针](ml-final.json) 再次验证无显式 group、有显式 group 两条 FIT/EVALUATE/APPLY 路径成功，默认参数在 standard 新工单上均为 28/30；全空正文仍返回具体失败原因。
