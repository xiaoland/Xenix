# 实现与验证

## 根本矛盾与边界

原词级预处理固定删除单字并使用业务停用词表，可能在模型看到文本之前丢掉否定、动作等信息；单次小留出集又被多组参数反复用于选型，无法提供足够稳定的泛化证据。两者分别属于可选择的表示策略与服务拥有的评估能力，不能靠增加 Agent 固定操作流程解决。

策略由 Agent 选择，服务执行并与模型一起保存；应用时复用保存的策略、词表与模型。额外业务清洗仍由 data.transform 显式提供，服务不暗中捕获任意前置变换。原则的持久 owner 是 Unit TDD，未修改 AGENTS.md。

## 已有证据

- 完整离线测试：303 passed；静态检查、隔离启动和 git diff --check 通过。
- Windows 打包至 dist/text-strategy-review 成功，新增评估模块包含在 PYZ 清单中；对应 smoke-package 退出码 0。日志分别为 build/text-strategy-package.log 与 build/text-strategy-packaged-smoke.log。
- 手工生产适配器实验覆盖 words、characters、pretokenized，保存后加载的预测与应用输出相同，所有分区的业务/模板组重叠数为零，数值标签的折外评估有效。
- 三种默认候选在确认任务历史数据上的交叉验证准确率分别约 77.78%、77.78%、75.56%；这是历史选型指标，不是新批次验收分数，也不是挑选默认参数的 oracle。
- 模拟缺少新增字段的旧 pickle 对象形状后，保存/加载预测保持一致；此实验不等于覆盖所有历史二进制制品。
- 只有一个独立组或各训练分区仅含一个类别时，返回验证不可用/不完整及原因，不给成功子集的总体分数。
- 未新增自动化测试函数，更新既有服务生命周期覆盖，移除不再使用的旧算法测试副本；手工脚本不加入自动化入口。

## 本轮真实运行

使用已有 DeepSeek 设置运行分流 confirmation 单项，未修改题库或 oracle，程序检查、完整性与独立 Judge 均通过；37 轮、60 次工具调用（1 次参数错误后恢复）、2,165,581 tokens，Subject 527.09 秒。该运行与 Windows 打包验证并行，因此耗时不能作为与历史运行的严格性能对比。

重新按交付表 artifact://354 的实际 suggested_queue 列逐行核对 oracle，28/30 正确（93.33%），达到 90% 门槛；保存的模型 120 被第二轮复用。不要引用程序汇总的 best candidate 100% 作为模型准确率：它枚举了描述列的候选映射，Judge 的职责是选择实际预测列。本轮独立核对确认通过不是这个最大候选分数造成的假阳性。

剩余两项错分是英文 invoice 否定及 return from travel 的词义；本轮未把它们隐藏或当作已解决。Agent 共训练 11 个候选/验证模型（包括额外手工分块验证及 channel 捷径演示），说明复用服务能力后的决策成本仍有优化空间。这不是本轮机制修复后的性能改善证据，也不构成全题库已通过的结论。原始报告和实际预测核对见 [本轮结果](live-confirmation.json)。
