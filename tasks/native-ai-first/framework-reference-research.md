# Framework Reference Research

## Status

- Mode: Explore.
- Purpose: capture useful design patterns from LangGraph, Vercel AI SDK, and PydanticAI without handing Xenix core contracts to a third-party runtime.
- Sources checked on 2026-05-11.

## LangGraph

Official facts:

- LangGraph focuses on low-level infrastructure for long-running, stateful workflows and agents.
- Its documented benefits include durable execution, human-in-the-loop, memory, and debugging.
- Durable execution requires persistence, thread identifiers, deterministic replay, and wrapping side effects in tasks.
- Persistence stores graph state as checkpoints organized by threads.
- Human-in-the-loop and interrupts use persisted graph state so execution can pause and resume.

Useful Xenix takeaways:

- Use explicit run identifiers and thread identifiers.
- Keep side effects idempotent or recorded with stable keys.
- Separate workflow state from user-visible messages.
- Keep replay constraints visible in tests.

Risk for first slice:

- LangGraph checkpoint/thread state may duplicate Xenix conversation thread/message persistence.
- Direct adoption would require mapping LangGraph state snapshots to Xenix SQLite state.

Sources:

- https://docs.langchain.com/oss/python/langgraph
- https://docs.langchain.com/oss/python/langgraph/durable-execution
- https://docs.langchain.com/oss/python/langgraph/persistence
- https://docs.langchain.com/oss/python/langgraph/human-in-the-loop

## Vercel AI SDK

Official facts:

- `generateText` accepts a language model, `messages` or `prompt`, `tools`, `toolChoice`, `stopWhen`, `prepareStep`, and provider-specific options.
- Tool execution uses typed input schemas and `execute` handlers.
- Results expose final text, content parts, tool calls, tool results, steps, usage, and warnings.
- Provider registry centralizes providers and model ids.
- Language model middleware can wrap provider calls for guardrails, caching, logging, and similar cross-provider behavior.

Useful Xenix takeaways:

- Keep model/provider selection separate from tools.
- Keep tool definitions typed and handler-bound.
- Use step-level loop control with explicit stopping conditions.
- Keep provider-specific options behind the LLM provider boundary.

Risk for first slice:

- AI SDK is TypeScript-oriented and web/UI-stream oriented.
- Xenix needs Python/PySide6-native contracts and SQLite-backed persistence.

Sources:

- https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling
- https://vercel-ai.mintlify.app/reference/ai-sdk-core/generate-text
- https://ai-sdk.dev/docs/reference/ai-sdk-core/provider-registry
- https://ai-sdk.dev/docs/reference/ai-sdk-core/wrap-language-model

## PydanticAI

Official facts:

- PydanticAI `Agent` is a container for instructions, function tools/toolsets, structured output type, dependency type, LLM model, and model settings.
- Agents can run sync, async, streaming, event streaming, or iteratively over an underlying graph.
- Function tools let models take actions or retrieve information through registered Python functions.
- PydanticAI uses Pydantic to build JSON schema for tools and structured outputs, then validate returned data.
- Tool and output validation can feed errors back into the model.

Useful Xenix takeaways:

- Use Pydantic or SQLModel models as the source of tool JSON schemas.
- Keep typed dependency injection for service-backed tools.
- Represent structured final outputs separately from tool execution results.
- Stream canonical events for UI and persistence.

Risk for first slice:

- PydanticAI owns a high-level agent runtime and message/run semantics.
- Xenix needs a product-specific canonical Message contract and provider dialect layer.

Sources:

- https://pydantic.dev/docs/ai/core-concepts/agent/
- https://pydantic.dev/docs/ai/tools-toolsets/tools/
- https://pydantic.dev/docs/ai/core-concepts/output/

## DeepSeek

Official facts:

- DeepSeek documents `/chat/completions` with OpenAI-compatible messages.
- DeepSeek tool calls use `tools`, `tool_choice`, assistant `tool_calls`, and `tool` role messages with `tool_call_id`.
- DeepSeek currently supports function tools, a maximum of 128 functions, and optional strict mode through the beta base URL.
- DeepSeek tool call arguments are JSON generated by the model and require application-side validation.

Useful Xenix takeaways:

- DeepSeek can share most of the OpenAI-compatible chat completions provider dialect.
- Strict tool mode should be an optional provider capability.
- Tool result correlation uses `tool_call_id`.

Sources:

- https://api-docs.deepseek.com/api/create-chat-completion
- https://api-docs.deepseek.com/guides/tool_calls

## Literal OpenAI `/v1/completions`

Official facts:

- OpenAI `/v1/completions` accepts a `prompt` and returns `text_completion` choices.
- The API shape is prompt/text oriented.
- The documented models include `gpt-3.5-turbo-instruct`, `davinci-002`, and `babbage-002`.

Useful Xenix takeaway:

- Literal `/v1/completions` is a text provider dialect. Tool calling would require a prompted JSON protocol over text.

Resolved by user clarification:

- The required first-slice OpenAI dialect is OpenAI-compatible `/v1/chat/completions`.

Source:

- https://platform.openai.com/docs/api-reference/completions/create
