# Static Agent Skill Mechanism

## Objective & Hypothesis

Discuss a minimal static Agent Skill mechanism for Xenix Agent.

Hypothesis: Xenix does not need Codex/Claude/OpenClaw-style dynamic skill discovery. Built-in skills can live under `src/xenix/services/agent/skills/` and be loaded as dynamic prompt content by Agent Harness when relevant.

## Current Understanding

- Agent Skills standard centers on a skill directory containing `SKILL.md` with YAML frontmatter and Markdown instructions.
- Required frontmatter: `name`, `description`.
- Progressive disclosure is the main design point:
  1. small catalog loaded always
  2. full `SKILL.md` loaded only when activated
  3. extra resources loaded only when referenced
- Xenix Agent Harness already owns hidden system messages and provider-facing message projection.
- Xenix provider boundary currently has tools, but no general file-read tool; a minimal Xenix mechanism should not expose arbitrary local filesystem reads to the model.
- The following are permanent non-goals for Xenix Agent Skill, not postponed scope:
  - user/global/repository skill discovery
  - third-party skill installation or marketplace distribution
  - environment/API-key injection
  - skill script execution
  - arbitrary local filesystem reads by the model
  - making skills user-owned mutable runtime state
- Runtime activation is now implemented as a Harness-owned internal tool:
  - provider sees a compact dynamic skill catalog system message
  - provider may call `agent.skill.activate`
  - Harness returns the selected skill body as provider-facing tool-result content
  - activation tool calls/results are persisted for provider protocol/audit but hidden from Chatbot timeline

## Candidate Shape

- Add a static skill catalog module under agent service.
- Parse/validate `SKILL.md` files from `src/xenix/services/agent/skills/` at build/development validation time.
- Add a compact available-skills catalog to provider context.
- Activate skills by Harness-side selection/injection or a constrained internal `agent.skill.activate` tool, not by filesystem discovery.
- Consider keeping PyYAML as a dev/build dependency if runtime consumes generated catalog artifacts instead of parsing YAML on every application launch.
- Strict development mode selected:
  - VSCode debug launch runs install, then generates the static catalog before app startup.
  - VSCode check/package tasks validate or regenerate the catalog explicitly.
  - PDM `dev`, `check`, `smoke`, and `package` scripts also enforce generation or validation.
  - `src/xenix/services/agent/skills/catalog.json` is a generated artifact and is ignored by git.
  - Runtime activation is implemented through the Harness-owned `agent.skill.activate` tool.

## Work In Progress: Resource Loading And Dev Visibility

- Dev-mode debugging should project internal `agent.skill.*` tools in the Chatbot timeline when `XENIX_ENV` is `development` or `dev`.
- Non-dev projection should keep hiding `agent.skill.*` because they are prompt-loading mechanics.
- `references/` and `assets/` are static skill resources:
  - discovered at catalog generation time
  - inlined into `catalog.json`
  - returned as a manifest in `agent.skill.activate`
  - readable only after activation through constrained internal tools
- Runtime consumes only `catalog.json`; `src/xenix/services/agent/skills/<skill>/` directories are dev/build inputs and must not be packaged as runtime assets.
- Resource reads must remain UTF-8 text, catalog-listed, bounded, and served from the generated catalog.
