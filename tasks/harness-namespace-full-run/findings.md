# 完整运行后的问题分流

28 项均已执行，机器结果为 15 pass、12 fail、1 partial。本文件记录独立核验，不覆盖 results.json 的机器判分。全量运行期间生产源码、case 和 Judge 保持冻结，结束指纹核对无变化；这里的新发现尚未实施修复。

## 已确认的旧 oracle ID 遗漏

堂食清洗的 `_result_dataset_ids` 只接受字符串 ID，忽略整数 ToolResult；XTT 元数据也被解析成字符串，不能命中整数 run_dataset_ids。其报告因此以 `no_readable_run_output_reference` 提前失败，而非读取交付后发现数据错误。见 [离线探针](manual-probes.json)。

另有八个旧用例复制的 `_is_run_descendant` 使用 `while isinstance(parent_id, str)`，无法遍历当前整数父链：履约清洗、聚类选择、预测验证、季节预测、文本词频、分组文本分类、主题发现、推荐排序。各 case 的最终内容仍需分别核验，不能因找到相同阻塞就把它们全部改判通过。履约清洗此次最终回答的五条记录和中位数 21 与 `_EXPECTED_ROWS` 一致，但对应 oracle 在读取内容之前就被父链识别挡住。

这些重复 helper 是旧题扫描内部对象图找答案的遗留，与新业务题及已经修复的两群聚类/商品相似推荐所使用的公开交付读取方式分叉。后续应统一以实际交付内容为入口，不为旧 oracle 增加 Harness 操作流程，也不只在每份拷贝上追加兼容分支。

离线调用全部八个原 helper，给出同一合法整数父链（派生 Dataset 2 指向源 Dataset 1），八个均返回 False；具体结果保存在 manual-probes.json。该探针只证明判题路径失效，不替代真实输出验收。

## 堂食清洗：旧成功定义本身需要修正

本次交付 486,119 行、47 列，保留 330 行完全相同的明细，并移除三个零信息列；旧 oracle 固定要求 485,789 行、50 列且去除全行重复。原题只有“清洗”，并未要求这一特定形状或无条件去重。

对原始 116 MB 文件的独立统计确认：有效明细为 486,119 × 50，去重后为 485,789 × 50；涉及重复明细的 231 个订单，保留明细时 231 个销售金额合计都与订单金额一致，去重后仅 57 个一致。全体 87,678 个订单中，对账一致数从 87,355 降到 87,181。模型答复引用的数字与独立计算完全相同，见 [原始文件复核](april-duplicate-evidence.json)。

这证明旧 oracle 把唯一行集合相同视为业务明细保全不成立，行的重复次数具有业务意义。不能把之前更便宜的机器 pass 自动当成更高效的正确清洗，也不能因为新输出不符合固定形状就定为产品回归。当前证据支持保留这些明细；“分次录入”的具体业务成因仍是模型解释，不由金额对账单独证明。三列删除与其他类型/缺失值处理另属清洗契约问题，未借此次复核把整份输出自动认证为完全正确。

## 补货解释与 Judge 漏判再次出现

标准补货报告为 pass，采购表达到正确最优毛利 1,845、成本 2,920、18 箱，但最终答复仍称仓容而非预算限制收益。独立穷举相同报价、到货条件与 18 箱限制，仅移除预算上限，可以取得毛利 1,865、成本 3,010：Q203 两批，Q102、Q305、Q509、Q510 各一批。见 [枚举证据](manual-probes.json)。最优采购点剩余 80 元不能支持预算无影响的推断。

这个解释问题在之前 G0/G1 以及当前解耦目录下都存在，且 Judge 仍漏判。它属于解释用事实与计算支持不足，不能宣称目录解耦已解决，也不能只按机器 pass 统计正确交付。

## 下一处工具接口问题：清洗元数据的占位标签

履约清洗已经查询元数据并读取参考资料，随后仍把 `single_column`、`multiple_columns` 当作 params 的真实字段使用；先在 validation.non_negative 失败，修正单列字段后又在 text.trim 失败。两次反馈分别要求 column_index/column_name、column_indexes/column_names。

`cleaning/catalog.py` 的各 operation.params 列表使用这些占位标签，而真实字段放在另一处 column_reference 说明中，且那里的键又是 single/multiple。执行器没有接受这些伪字段。模型需要在三种命名之间做翻译，是明确的调用者负担；后续应直接呈现真实参数名，消除这层间接说明，不是继续裁掉上下文。这一轨迹能确认误用方式，不能证明它解释了所有清洗工具失败。

## 已确认的 Harness 中止：未激活工具未进入恢复流程

business.restock.v1.margin_higher 在第一个采样请求以 `llm_tool_not_exposed` 中止，没有 canonical ToolCall/ToolResult 或最终回答。这是实际运行失败，不是 oracle 误判。`llm/providers.py` 的普通响应解析和流式聚合各有一处：如果工具名不在本轮发送的 definitions 中，就在构建 ProviderResponse 之前抛异常。

LLM registry 本来已经在调用入口检查 advertised scope，Conversation 又会把调用异常转成 canonical ToolFailure 供模型修复；Provider 层更早的拒绝绕过了这条路径。懒加载目录明示工具名称后，模型偶尔请求未激活工具是可恢复的选择错误，不应直接终止业务任务。后续应让 Provider 保留调用及 usage，由统一调用边界解析身份并生成可恢复反馈，避免机械地把 wire 名下划线替换成点而误认真实工具名。

该报告虽将 reported_subject_tokens 写成 0，但 admitted rounds=1、reported responses=0，usage 不完整；结果索引将整体 tokens 标为已观察下界，完整总量为 null。这不是免费完成，也不能据此声称性能提升。原报告没有保留被请求的具体工具名，故本次不推测其名称。

## 分组切分：存在合法划分，单次哈希划分仍可拒绝训练

主题发现本次 28 轮、729,018 tokens，六次 model.train 返回同一类别缺席错误。轨迹先修改 phrase_mode、class_weight 等模型参数，再重排数据，最后人为构造 pos 分组才训练成功。模型参数不会改变固定输入、分组和 seed 的划分结果，当前反馈也没有告诉调用者缺失的类别、各类分组数量及可行性。

`ml/preparation.py::_group_hash_positions` 按哈希排序分组、选最接近目标行数的前缀，随后 `_validate_target_credibility` 检查所有类别都在两侧；前缀不满足时直接拒绝，没有寻找已有可行划分。使用相同原始题目和正确主题标签的离线探针得到 12 个独立文本组，每类 4 组，每组 3 行；从每类选一组作为 holdout 就能得到 27/9 行、类别齐全且无重叠的合法划分。现有算法在 seed 0–19 中有 14 个拒绝训练，见 [group-split-evidence.json](group-split-evidence.json)。这是算法边界的可复现证据；探针使用原始文件摘要，不冒充对 live 派生文件摘要与学习标签的逐字重放。

下一步应先让分组分类切分利用类别信息寻找可行划分；对确实不可能的情况反馈具体类别/分组事实。不能把失败后改数据、重复训练当成 Agent 的必经流程，也不能把随机抽中的坏划分描述成数据本身无法评估。

## 主题发现还存在旧输出格式约束

整数父链之外，主题题 `_matches_topic_assignments` 仍要求恰好包含 dominant_topic、topic_score、topic_1_share 等 LDA 风格列；原题却只要求三类主题标注、可复用分类和质量评估。当前 Agent 选用聚类发现主题，再训练分类器，最终交付 theme_code/theme_label 和置信度；不能仅因它未采用隐藏的 LDA 输出列就认定业务未完成。后续需要按实际标注和评估内容判断，也不能只修整数 helper 就把这题当成已恢复可信。

## 图表题 partial 有实际内容问题

图表成功 ToolCall 的 spec 使用 window sum 计算 total，却没有表达全表分母。使用记录的 spec、原始 fixture 和当前未修改渲染器离线重渲染，柱长仍是 30/25/20/10，但图中各地区的 share 标签为 North 100.0%、South 66.7%、West 50.0%、East 29.4%，与最终回答的正确占比冲突。可见文本与相同 oracle 投影都保留了错误标签，见 [graph-replay-evidence.json](graph-replay-evidence.json)。这不是把不可见 SVG 当作无标签造成的纯误判；原报告只给 partial，而这些错误百分比已经影响事实正确性。

第一次 graph 调用将正确占比作为 inline values 传入，触发 Dataset 来源冲突；模型随后移除 inline data，改写为有上述错误的 transform。这条轨迹说明显式错误避免了先前静默替换，却没有彻底解决调用者的数据来源表达负担。当前提交的错误契约不能被宣传为图表问题已完全解决。离线重渲染是可复现的派生证据，不是原临时 runtime 中留存的 SVG。

## 收入标准题的机器通过仍漏掉首答合计错误

两次四区域交付和排序正确，但首答内联表的净回款合计写成 84,450；四项 40,750 + 32,900 + 22,000 − 1,200 应为 94,450，且同表 108,650.75 − 14,200.75 也等于 94,450。第二次净回款合计 83,750 正确。首次答复和四行导出均保存在原报告 turns[0].delivery_evidence，不能只看 subject.outcome 中的末次答复就判定旧解释问题全部消失。

此次没有重现旧的“西区退款更多”等具体句子，但出现了新的实质数字矛盾，Judge 仍判 pass。它与补货标准题共同说明机器 pass 不是完整正确性的保证，性能表只呈现原始判分，不能据此宣称正确交付的成本降低。

收入确认变体本次同样机器 pass，两轮区域净额、合计及修订差异正确，旧的“东区两笔 cancelled”和“11,000 为整单退款”没有重现。但首答反事实说明将“若纳入 O20，South 的 paid 金额”也写成 1,500；O20 为 2,700，只有扣掉 1,200 退款后的净额才是 1,500。它不改变实际交付表的正确数字，仍是解释中的新数值错误，不能据此次通过断言解释问题已经根除。

## 下一轮优先级

1. **工具调用恢复边界**：Provider 负责保留 wire 调用与 usage，Registry 统一解析注册身份和参数，Conversation 形成可继续对话的调用结果；不要让目录可见性在两个位置变成中止任务的边界。先处理本次已确认的未暴露工具错误，保留原始工具名以便诊断。
2. **恢复 benchmark 的判题可信度**：把九处受整数 ID 影响的旧 oracle 收敛到实际公开交付读取；同时移除堂食无条件去重、主题固定 LDA 输出格式等隐藏要求。正确替代表示与真正不正确的数据要分别检验，不能通过提示词强迫 Agent 满足旧实现形状。
3. **分组分类的切分实现与反馈**：先解决明明有合法划分却因哈希前缀不佳拒绝训练；对确实无法满足评估要求的情况，单独判断训练和评估是否应解耦，并报告具体缺失事实。模型超参数重试不能修复固定的错误划分。
4. **清洗参数与图表来源接口**：清洗 metadata 使用执行器真实参数名；图表需要让 Dataset 来源和图内计算的关系更直接，不能把“有冲突就报错”当作数据来源设计已完成。

本轮不因这些发现中途修改测量对象；也不启动泛化的流程提示词改造。任务目标扩张、解释缺少计算支持仍按之前约定单独处理。下一轮先消除会终止会话的具体 Harness 缺陷，并恢复可信的结果反馈，再用 benchmark 判断进一步目录精简是否有效。

## 批量训练被单一失败压缩成整批异常

预测验证一次 model.train 提交 seasonal_naive、holt_winters、sarima 三个候选，工具仅返回任务 56 失败及“至少需要 90 期历史”；该 ToolFailure 没有同批任务 ID、其他候选状态、已完成结果或待完成状态。`ml_service.py:413` 的 wait_for_training_models 已取得 related_tasks 和 trained_models，却在发现任一 FAILED/CANCELLED 时立即抛第一个错误；因此 `_model_tools.py` 的完整训练反馈根本没有机会执行。这是已确认的批量返回契约缺陷，适用于 train 和 hyper_train；不能仅靠进一步压缩训练结果正文修复。

后续应按候选返回完成、失败与仍运行的状态及必要链接，保留可用结果与具体失败原因，让部分失败仍然可观察。当前轨迹不能单靠失败 ToolResult 证明另外两个候选当时是否已经成功，故这里不把其未知状态写成既成事实。

## 补货确认变体超时：原因尚未定到 Provider 或本地调度

business.restock.v1.confirmation 触发原定 900 秒外部时限，run_status=budget_exceeded、failure_kind=process_wall_time_exceeded。最后完整 usage 在 16.84 秒，记录 5 轮、25,820 tokens；后续没有新的 sampling_started 或完整 usage。超时前以只读方式检查临时会话，最后为 sequence 17 的 pending_llm_sampling，之前 sequence 16 是 failed ToolResult，sequence 15 为 data.query 调用。

待采样状态不等于已经向 Provider 发出了请求，因此当前证据不能区分 Provider 流式等待、本地调度或采样准备阶段的阻塞。此前运行进度中的“模型响应未结束”应按这个更窄的边界解释。已执行的 SQL 失败、后续挂起与 worker 错误附注修改之间没有因果证明，不能直接归因于新目录或 worker 小修复。

保留此次失败，不用之后重跑成功覆盖。它的 token_usage、完整 ToolResult 计数和最终输出均未完成采集，25,820 是下界而非完整成本；后两项随后按冻结清单完成。若单独追查，需要在复现时捕获活动调用栈或采样阶段事件，再定位具体阻塞点。

## 分流确认：实际准确率 86.7%，Judge 此次正确挡住假候选

分流确认完成了模型保存和复用，但交付表 suggested_queue 和原始 prediction 均只有 26/30 正确，低于题目要求的 90%。对冻结表格与私有 truth 的独立逐条比较确认四个错误，见 [routing-confirmation-evidence.json](routing-confirmation-evidence.json)。这些工单包含当前诉求与其他话题的区分，不能把模型自己指出错误或建议人工复核当作已交付满足要求的保存模型。

报告结构检查的 accuracy=1.0 来自 channel 列的一种映射，不是实际建议队列。当前两阶段 oracle 把所有候选列及各自分数交给 Judge，Judge 按实际交付列给 usable_queue_labels=0、整体 fail；本次最终失败不是 oracle 误判。单看 semantic=pass 或最高候选分数会得到相反结论。调用者确实指定并复用了 model 68；后续改进目标是它在确认样本上的实际判断能力与采用证据，不能放宽判分或用未交付的人工纠正替代。

分流确认本次 23 轮、559,133 tokens，训练 6 次。第一次回答把同一 holdout 上两个参数设置得到相同分数解释为“不是偶然的 holdout”，这不构成独立验证；本次 Judge 并未因此降低 adoption_evidence。保存的完整回答使这一额外采用证据问题可供后续专项分析，本轮不重新写 Judge 原判分。
