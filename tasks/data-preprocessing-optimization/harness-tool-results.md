# Harness Tool Result Boundary

## Responsibility

Agent Harness gives the LLM a reliable base for interacting with real-world data:

- stable tool registry;
- compact tool facts;
- executable references;
- error boundaries;
- enough evidence to choose the next tool call.

Agent Harness should not pre-package human-facing explanation for the LLM.

## Provider-Facing Principle

Tool results are for LLM lookup and next-call planning only. They should not mix in human-facing presentation responsibility.

For this task:

- tool `result_payload` should be the canonical bounded machine result;
- spreadsheet inspection/structure should be represented as compact JSON;
- no Markdown table should be generated by a tool unless Markdown is deliberately the best machine-readable result shape for that specific tool;
- tools should not return `content_blocks` as a normal result surface;
- no duplicate markdown/profile payload should be persisted or replayed to the provider;
- if the user asks for a Markdown table or explanation, the LLM should compose that in an assistant message from the DSL and tool evidence.

## Current Issue

`ConversationStore._tool_result_to_text()` currently serializes the entire `AgentToolCallRow.result_payload` as provider-facing JSON.

Observed impact from the case thread:

- first `data.peek` result is about 28,006 JSON chars after wrapping;
- the next provider request input is 18,175 tokens;
- the provider sees both structured profile and `analysis.markdown`, duplicating content.

## Desired Direction

Do not maintain separate persisted and provider-facing tool result truths by default. The persisted tool `result_payload` should itself be compact, operation-oriented, and suitable for provider replay.

`AgentToolCallRow` is still not just a result store. It remains the execution ledger for a tool invocation: tool name, arguments, status, request/result message pairing, error summary, observability correlation, artifact lineage, and UI timeline projection. Removing the persisted/provider-facing result split does not by itself imply deleting `agent_tool_call`.

`ToolExecutionResult` should be only the in-process return envelope from a tool handler to Agent Harness. It should not be a second result truth. Its normal payload field should become or map directly to the canonical `result_payload`; separate provider payloads and normal `content_blocks` should disappear from ordinary tool execution.

The canonical tool result should preserve:

- tool name and status;
- executable ids and names;
- compact executable schema/inspection facts;
- bounded errors and repair hints;
- artifact ids or task ids when applicable.

The canonical tool result should omit or compact:

- human-facing markdown;
- large repeated summaries;
- full frequency tables unless explicitly needed for the next call;
- raw values beyond bounded samples.

If a tool must keep bulky debug/audit material later, that material needs an explicitly named owner such as an artifact, task log, or diagnostics surface. It should not silently live beside the LLM-facing result as a parallel truth.

Audit/diagnostic collection belongs inside the tool implementation, service logs, task logs, traces, or artifacts. Capturing observability material in the function output is an anti-pattern because it mixes runtime observability with the business/tool contract.

## Compact Table Pattern

For repeated object arrays in LLM-facing tool results, prefer a compact schema-plus-rows representation:

```json
{
  "_schema": {"tool_name": 0, "position": 1, "samples": 2},
  "data": [
    ["品项销售明细", 0, ["城市", "佛山市"]],
    ["column_2", 1, ["机构编码", "C7"]]
  ]
}
```

This pattern should be considered cross-tool, not `data.peek`-specific. It preserves structure while reducing repeated key noise.

## LLM Boundary Constraint

This task should not broaden into a full LLM service boundary refactor. However, if existing provider-shaped seams directly block tool-result convergence, they can be touched locally.

Do not change production implementation shape merely to support tests. Test doubles may satisfy the same canonical interface, but production seams should exist for product/runtime reasons, not because tests need a bypass.
