# Harness Tool Result Boundary

## Responsibility

Agent Harness gives the LLM a reliable base for interacting with real-world data:

- stable tool registry;
- compact tool facts;
- executable references;
- error boundaries;
- enough evidence to choose the next tool call.

Agent Harness should not pre-package human-facing explanation for the LLM.

## Provider-Facing Principle

Provider-facing tool results are for LLM lookup and next-call planning only. They should not mix in human-facing presentation responsibility.

For this task:

- spreadsheet structure should be represented as JSON DSL;
- no provider-facing Markdown table should be generated by the tool;
- no duplicate markdown/profile payload should be replayed to the provider;
- if the user asks for a Markdown table or explanation, the LLM should compose that in an assistant message from the DSL and tool evidence.

## Current Issue

`ConversationStore._tool_result_to_text()` currently serializes the entire `AgentToolCallRow.result_payload` as provider-facing JSON.

Observed impact from the case thread:

- first `data.peek` result is about 28,006 JSON chars after wrapping;
- the next provider request input is 18,175 tokens;
- the provider sees both structured profile and `analysis.markdown`, duplicating content.

## Desired Direction

Keep rich persisted payloads where useful for audit/debugging, but add a provider-facing projection that is compact and operation-oriented.

The projection should preserve:

- tool name and status;
- executable ids and names;
- compact structure DSL;
- bounded errors and repair hints;
- artifact ids or task ids when applicable.

The projection should omit or compact:

- human-facing markdown;
- large repeated summaries;
- full frequency tables unless explicitly needed for the next call;
- raw values beyond bounded samples.
