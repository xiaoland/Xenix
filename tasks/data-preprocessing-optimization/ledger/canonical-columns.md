# Canonical Column References

## Current Decision

- Do not store canonical column names directly on `dataset` table in the current slice.
- Registered datasets now point at app-owned materialized tables, but schema metadata is still a runtime-derived projection unless a later workstream deliberately introduces immutable schema snapshots.
- Make canonical column names a deterministic projection from a shared thin tabular schema resolver used by import, `data.query`, `data.transform`, cleaning/tokenization, and ML-facing registered-dataset loading.
- If persistence is later needed for performance or immutability, introduce a separate schema snapshot/cache with source fingerprint and resolver version rather than expanding `dataset` row semantics.

## Column Index

Column index is useful and should be exposed as a separate reference channel.

- SQL-oriented tools should continue to use canonical names because SQL has a natural name-based column model.
- Future operation-shaped tools may expose distinct fields such as `column_names` and `column_indexes`.
- Service validation should reject mixed or ambiguous references.

Do not use a single field that accepts both names and indexes.

Bad:

```json
{"columns": ["column_23", 22]}
```

Better:

```json
{"column_names": ["column_23"]}
```

or:

```json
{"column_indexes": [22]}
```

## Canonical Naming Rules

Preserve original names only when they are:

- non-empty;
- not generated by a known loader;
- unique after normalization;
- stable enough to quote in SQL.

Generate deterministic `column_<1_based_index>` names for:

- empty names;
- known loader-generated placeholder names;
- duplicate names after normalization;
- names that cannot be represented safely or consistently across supported loaders.

Keep original/loader names and coordinate indexes as evidence in the DSL, but make `tool_name` the downstream executable authority.

## Mechanical Detection Rules

Empty names:

- `None`
- empty string
- all-whitespace string

Known loader placeholders:

- pandas style: `Unnamed: <n>`
- Polars/calamine style: `__UNNAMED__<n>`
- any other explicit known-loader placeholder added to the loader wrapper test table

Duplicates:

- exact duplicate after string conversion and trim
- duplicate after resolver normalization

Unstable names:

- control characters
- embedded newlines
- overlong text beyond the resolver threshold
- non-string header values whose string representation may differ by loader
- names that cannot roundtrip through JSON plus quoted SQL in supported tools

## Boundary Rule

The logic that recognizes pandas/Polars placeholder conventions is loader-specific and must stay in the thin loader wrapper. Downstream services should only see `tool_name`, `source_name`, `loader_name`, `index`, and explicit `name_source` facts.

LLM-facing results should normally expose only executable names, indexes, and bounded samples. Loader names and `name_source` are internal diagnostics unless a specific repair flow proves they need to be surfaced.

## Authority

`tool_name` is the executable column authority.

`index`, `source_name`, `loader_name`, and samples are evidence and traceability fields, not execution keys.
