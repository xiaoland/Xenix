# 分流超轮：可证实的机制、放大因素与后续实验

调查基线为 `ae83667`，仅增加本 packet 的诊断材料；未修改生产代码、Skills、benchmark 题面、oracle 或预算。使用六个保存的真实分流轨迹，以及最终版本十二组原参数的原生 FIT → EVALUATE → APPLY（历史与新批次各一次），新增 Subject/Judge 调用为零。原生探针不是自动化测试，不由 pytest 收集。

后续用户纠正了修复原则：benchmark 不应在生产 Harness 之外另设采样配额，训练反馈属于 Harness 自身缺陷。下文保留当时的调查与建议，最终授权后的设计、实现和新增验证以 [修复记录](implementation.md) 为准；不再把十二轮或单任务 token 限制当成产品本身的执行约束。

## 结论

当前超轮的共同机制是：模型持续扩展“是否采用”的证据与展示范围，而 Harness 只依据本次回复是否还请求 Tool 决定继续；外部 benchmark 的十二轮是不可见的整体上限，到达后直接拒绝下一次采样。模型已经得到分析器、报告入口和估算错误率所需事实，也可能继续比较、检查历史预测和做图，最终没有把结果发给用户。这是已观察的交付收束缺口，不能简化成某条异常被吞掉、缺少某个工具或训练总是失败。

同时，不能把全部追加训练称为无价值：最终版本默认候选的留出准确率只有 77.8%，改一个词频参数后达到 94.4%，探索具有明确的初始动机。但十二次原参数实验又发现，confirmation 中较高留出分数的候选只有 86.7% 新批准确率。收束和选模证据是两层问题；只让模型早点回复，不能宣布业务任务已通过。

## Harness 的继续条件与预算边界

[`harness_service.py`](../../src/xenix/services/agent/harness_service.py:569) 在没有 staged calls 时 finalize assistant、发送最终快照并 return；有调用则完成 Tool 结果、更新 frontier 并继续。真实 `30541015`、`28ce99b4` 的首条终答也证明这一路径正常。失败所在请求的最后采样仍请求工具，没有一份已生成的正常终答等待被释放。

[`providers.py`](../../src/xenix/services/llm/providers.py:329) 使用 `tool_choice=auto`，没有强迫模型必须调用工具；64 KiB Tool 分页阈值也没有造成这些 13 KiB 左右训练结果被分页，六次没有 `result.page` 调用。原报告和新原生实验均有真实模型/评估入口，不能把它们说成没有交付 handle。

[`runner.py`](../../tests/e2e/agent_harness/_infra/runner.py:135) 的 `_BoundedLLMService` 只在请求前计数/拒绝，未向 provider messages 添加剩余预算；[`BusinessTask.build_submissions`](../../tests/e2e/agent_harness/_infra/business_tasks.py:110) 分别发送两个请求，第二个请求不提前告诉模型。第一个请求用了九或十轮后，下一请求只能再用三或两輪。生产 Harness 本身也没有可见的剩余轮次字段。该事实解释了为何无法从模型行为推断它主动选择无视十二轮限制。

十二轮是当前评测的效率约束，不因失败自动认定它不合理；两项请求可用更短的合法交付完成，但尚未用新的真实 Agent 对照证明稳定可达。也不应要求模型预知未来用户会追加什么，或为当前未知的下一请求机械预留固定轮数。

## 原生实验：追加训练的动机与质量风险

执行 `.venv/Scripts/python.exe tasks/harness-routing-diagnosis/probe_model_evidence.py --output tasks/harness-routing-diagnosis/model-evidence.json`。原参数来自最终两条 trace，保留原 role bindings、相同九十条历史及当前分组策略；每项实际训练、评估，再分别应用于历史和本变体的新批次。结果见 [原生证据](model-evidence.json)。两变体历史相同，没有把新批标签用于训练或供给 Subject。

| 配置 | 留出准确率 | standard 新批 | confirmation 新批 |
| --- | ---: | ---: | ---: |
| 默认单词，词频下限 1 | 14/18，77.8% | 28/30，93.3% | 28/30，93.3% |
| 单词加词组，词频下限 1 | 14/18，77.8% | 28/30，93.3% | 27/30，90.0% |
| 词频下限 2，单词或单词加词组 | 17/18，94.4% | 28/30，93.3% | 26/30，86.7% |

所以“再试一次”并非全无依据；但在同一小留出集上反复比较后继续把最高分当作新独立证据，并不成立。新批成绩也不能反过来用于指定默认参数作为答案，否则等于用评测目标挑模型。本次只用它判断“收束修复能否独自解决后续问题”，不改九成要求、不宣布 oracle 误报。

[`text_analysis.py`](../../src/xenix/services/ml/models/text_analysis.py:315) 保留两份模型：一份仅在留出之外训练以供评估，一份在全部有效历史上 refit 以供 apply。前五类候选对完整历史的 apply 都达到 90/90。再查这些历史预测不能提供新的未见样本误分率证据。当前原生执行确实实现了这种区分，属于调用方需要理解的统计语义，不是服务没有留出验证。

当前参数比较全部重用相同的 18 行、3 个业务组的外部留出；固定切分改善可复现性，并不增加独立样本。保存终答 `28ce99b4` 曾把三种配置同为 88.9% 解释成“不是幸运切分”，这项结论没有独立切分依据。完整任务当时在后续请求超轮而没有进入 Judge，因此不能声称该说明已通过语义验收。

原 trace 没有保存每个 train 返回的完整 trained_model_ids 对照，最终两条也没有选型终答；不能由后续 apply 的 id 精确恢复它采用了哪一参数。这里证实的是高留出分候选的质量风险，未冒称确认最终选择。

## Tool 反馈的可用性与规模

[`ModelTools._training_completion`](../../src/xenix/services/agent/_model_tools.py:225) 把 FIT/EVALUATE 两份持久化 result payload 原样装入 results。原生单候选返回约 1.34 万字节，其中 results 约 1.29 万字节；模型及评估报告两个公开链接确实存在，accuracy、混淆矩阵和评估样本数也已经返回。

payload 同时含评估/应用模型文件路径、多种不适用的模型领域空值、重复 split/preparation、指纹和向量化内部事实；[`model.task.query`](../../src/xenix/services/agent/_model_tools.py:313) 又返回完整任务行。真实 `b42c66b7` 的一次查询为 42,253 bytes，最终两条全部 Tool 输出分别为 116,783/120,792 bytes。它们把业务比较结果埋在较大的内部记录中，是明确的接口复杂性；“精简后一定更早完成”仍是假设，尚无同一上下文的对照结果。

## 建议的最小下一步

优先做一次有控制变量的完成决策实验，保留 Subject、两个请求、单任务预算、数据和 oracle。针对同一个“训练已返回足够证据”的 provider 上下文，比较当前反馈、精简训练反馈、以及仅补充真实剩余资源三种条件；记录下一动作是交付、处理实质缺口还是继续展示。随后只对有效干预重放整项任务，不能把一个 checkpoint 的终答倾向当作端到端通过。现有 trace 没有完整中间 provider 上下文，实验需要在独立诊断运行中捕获，不从存储缺失的 ToolResult 编造原对话。

最值得准备的产品修改是训练返回按每个候选组织“模型入口、报告入口、参数、关键评估、样本/分组口径与模型复用方式”，完整诊断继续保存在报告和按需查询中；这是反馈接口简化，不是再增加一份必须先检查的流程。实际预算信息由拥有预算的调用者提供，不复制到 Skill，也不按剩余轮数强制封禁工具或另加完成裁判。上述两项都需要实验验证收益，当前没有修改源码。

选模质量另行处理：需要区分用于比较候选的证据和用于估计外推效果的证据；具体采用分组交叉验证、独立确认还是收窄选择声明，应按样本量与模型成本设计，不能把“多跑几个随机种子直到超过九成”当成解决方案。本调查不扩写成 ML 全面重构，也不拿新批真值反向选参数。

没有新增回归测试、benchmark 自测或付费 LLM 运行。工具校验摩擦作为次要缺陷保留；不存在已验证的单条提示修正能够解决所有超轮的结论。
