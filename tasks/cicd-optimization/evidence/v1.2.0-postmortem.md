## Actual Promotion and Release Topology

At release start, accepted Knowledge Base commits were on the `develop` line,
`origin/develop` also contained the v1.1.0 version commit, and `origin/main`
contained a separate Setup-publication fix. A clean release worktree joined those
lines, reconciled publication behavior, bumped the version, and pushed the resulting
commit to `develop` together with `v1.2.0`.

There was no GitHub `develop -> main` promotion PR. There was also no direct local
merge pushed to `main`: `main` remained at `42b5dbd`. The accepted tag eventually
resolved to `9fccee1` on the `develop` line. Production Publish first failed from the
tag because the protected Environment admitted only `main`, then succeeded when
dispatched from the older `main` commit using the candidate version and digest.

This is evidence of an undefined promotion/release authority, not evidence that a
direct push to `main` occurred.

## Diagnosed Causes

### Late integration evidence

Native CI triggers on PRs and `main` pushes. It does not trigger on `develop`
pushes. Because the relevant work was accumulated on `develop` without a promotion
PR, release preparation became the first GitHub Windows CI execution of the exact
integrated line.

A test-only CI gate would not have found every issue: locked Visual C++ dependency
discovery and frozen packaged smoke require Release Readiness. Both ordinary CI and
tag-bound release closure are needed. The selected future boundary is Native CI on
the `develop -> main` promotion PR, followed by Release Readiness only when an
immutable tag on the promoted `main` commit starts release.

### Monolithic and lossy candidate feedback

The candidate exposes `pdm run test`, one aggregate `Build unsigned candidate`, and
one aggregate upload. The build composite contains five materially different
boundaries. The original frozen-smoke wrapper retained only an exit code and deleted
the temporary runtime, so one full candidate supplied no actionable cause.

Pytest uses two subprocess cohorts, but GitHub exposes them as one step. Buffered
dot output and variable Windows runner performance made a progressing cohort look
indistinguishable from a hang. There was no workflow-owned timeout/diagnostic
protocol, leading to human cancellation decisions.

### Product lifecycle defects

The candidate correctly exposed two application defects:

- closing repeated MainWindow instances did not shut down the three Knowledge
  service workers at the application composition boundary;
- dialog refresh tasks used Qt's global thread pool and could outlive their window,
  allowing SQLite disposal to overtake an active query.

Cross-order repair also moved process-global Python/native imports off a daemon
startup thread. These are real release blockers, not CI false positives. The process
worked as a safety gate; the improvement is to exercise the same topology earlier.

### Acceptance boundary mismatch

`import_file()` promises Canonical Ready. Import-to-Derivation notification is a
post-commit asynchronous handoff. Packaged smoke originally required the derivation
row at the exact instant import returned. CI timing exposed that invalid synchronous
assumption. The accepted fix waits with a bound for eventual visibility without
coupling the services.

### Transfer opacity and duplication

The accepted candidate's upload/remote verification took about 47 minutes. For every
artifact, the uploader:

1. hashes the local file;
2. performs a non-resumable `put_object_from_file`;
3. downloads the full remote object and hashes it again.

It emits no progress. Cancellation can leave a private partial object, safely
isolated by the manifest-digest prefix, but cannot resume it. The safety shape is
good; the transfer and observability shape is not.

### Release-state ambiguity

The final `v1.2.0` tag was used as a movable candidate pointer while pre-publication
fixes accumulated. Lease-protected moves prevented blind overwrite, and no complete
candidate existed at those points, but a SemVer release tag should lock one Release
SHA and start one tag-bound release pipeline, not carry mutable workflow state. A
product correction after tagging therefore uses a new version; only transient
infrastructure work may rerun against the unchanged tag.

Candidate requires a `v*` tag while Publish's Environment admits only `main`.
Neither the workflow dispatch surface nor durable documentation explains that split.
The first Publish therefore accepted an invocation that could only fail before
runner allocation. The successful Publish then ran publisher code from a different
commit than the candidate.

## Safety Properties That Worked

- Every failed build/test run stopped before public publication.
- Candidate objects were private and partitioned by version plus manifest digest.
- Partial upload did not become a complete candidate because the manifest was
  committed only after artifact verification.
- Production publication authenticated the exact accepted manifest digest.
- Immutable published packages used create-only behavior.
- Feeds were written last, the prior feed was snapshotted, and the stable Setup alias
  and public Range/hash behavior were verified.

These observations identify the useful safety outcomes, but do not require keeping
the Candidate mechanism that happened to provide some of them.

## Adopted Simplification

The postmortem originally motivated a better-separated Candidate/Publish protocol.
Final review rejected that direction as disproportionate. The approved target
removes Candidate entirely: an eligible immutable tag starts one workflow that
builds the exact Tag SHA, directly uploads create-only version artifacts, verifies
them, and changes one authoritative public visibility point last.

The useful safety primitives above remain; the private candidate prefix, Candidate
Environment, copied manifest digest, second Publish dispatch, and second human
approval do not. Directly uploaded but feed-unreferenced intended-public artifacts
are an explicitly accepted tradeoff.
