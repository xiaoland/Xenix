# LLM Conversation / Agent Harness Boundary

## Objective

Establish an evidence-backed boundary between LLM Service, canonical interaction state, observability, and Agent Harness that improves maintainability and readability, corrects confirmed defects, and settles whether conversation persistence needs either a `Turn` or persistent `Run` abstraction.

## Guardrails

- Sir authorized investigation and task-packet restructuring on 2026-07-14. Product mutations remain whole-task-specific: the complete cross-owner cutover needs one approved Impact Handshake before it is applied.
- Do not treat an architecture preference as a defect without a reproduced failure or a violated invariant.
- Preserve only complete canonical conversation protocol units: a final LLM emission containing Tool Call Messages commits together with its Tool Result Messages. Domain side effects remain outside that SQLite transaction and may be orphaned by an accepted process-loss trade; preserve bounded completion-guard behavior, final-history convergence, and typed Chatbot projection.
- Keep provider configuration, transport, retry, response normalization, the Thread/Message interface, typed Message algebra, context projection, pending/final LLM Message lifecycle, AgentTool abstraction/registry/invocation, and canonical conversation state at the LLM boundary. Keep import coordination, sampling/tool-call policy, in-process step/guard/cancellation policy, and Chatbot-event projection at the Harness boundary. No third top-level conversation service is in scope.
- Observability is cross-cutting, not a third conversation owner: logs, traces, metrics, retry timing, and raw diagnostic wire data may be persisted by observability, but are never a source for conversation replay, tool-outcome reconstruction, or state repair.
- Tool interface and implementation are different things, but `AgentTool` is LLM-owned. LLM Service owns the Tool protocol, registry, exposed-scope validation, and invocation operation. Concrete adapters implement the LLM protocol and are wired by composition; Harness bootstrap may call the registration interface but never owns registry/lookup/dispatch/lifecycle. LLM Service never imports Harness or concrete/domain tool modules.
- SQLite remains the authority for bounded local application state. Forward migrations, fresh bootstrap, upgrade, ORM readability, and focused repository behavior must be proven for any schema change.
- Do not commit, publish, or change external state without separate explicit authority.

## Current Truth

- The task is in Solidify posture. The target contract is settled in this task packet; no product-code mutation is authorized yet.
- Production composition is `UI -> Agent Harness -> LLM Service -> provider adapter -> provider`; Harness currently owns `ConversationStore` orchestration over SQLite and the current `LLMService` has no conversation persistence.
- Two adapter boundary defects are confirmed: unexposed provider tool calls can be silently discarded before Harness authorization, and malformed-but-valid provider payloads can escape as raw `IndexError`.
- Synchronous and streaming Harness loops duplicate a large causal state machine. Text streaming is currently buffered for retry safety; this is a product/performance trade-off, not yet a defect.
- A temporary-DB restart probe confirms that a new user message in a reopened thread sends `system -> prior user -> prior assistant -> current user` to the provider. The reported low token use does not establish historical-context loss.
- `Turn` and `Run` are distinct persistent aggregates in the current system, but both group one linear user-to-LLM interaction. The earlier no-Turn counterfactual promoted Run to Turn's causal role and therefore did not fully remove the abstraction.
- A failure path can persist `Run=FAILED` while leaving `Turn=OPEN`; this conflicts with terminal-state convergence and must be designed and tested explicitly.
- Sir selected the refined ownership form of Option A: LLM Service owns canonical conversation state, not observability logs. Sir then removed the requirement for automatic cross-process execution recovery; under that constraint, persistent Run no longer earns an independent authority role.
- Sir corrected two earlier design assumptions: AgentTool is owned by LLM Service through dependency inversion, and typed Message is a canonical conversation-state atom rather than a UI/provider transcript projection. Harness must never be an invocation port called by LLM.
- An official-ecosystem comparison found no reason to reverse that corrected ownership topology. It does require treating LLM Service as a Conversation Kernel rather than a narrow ChatModel wrapper, keeping context compilation non-mutating, and preserving call identity across provider projections. Ecosystem Runs/checkpoints pay for durable continuation capabilities that Xenix now explicitly declines.
- The current favored lifecycle is the two-sided protocol in [11-client-llm-message-protocol.md](11-client-llm-message-protocol.md): finalized Client/LLM Messages are durable; a pending sampling Message makes an incomplete tool exchange provisional; a final tool-calling LLM emission and all of its Results commit together; and no persisted identity spans the Harness loop. Harness owns Chatbot activity projection, including the UI's “Thinking” indicator; live policy is in-memory and is not resumed after exit.
- A provider response normalizes to an ordered sequence of independent canonical Messages: `AssistantMessage` and `ToolCallMessage` are separate LLM-side entries, and `ToolResultMessage` directly references its Call. A provider envelope is an adapter projection, not SQLite's canonical shape; there is no shadow response-group identifier.
- Provider history transport remains adapter-specific, but a shared mutable remote Conversation is not currently allowed: it can advance before the local Message commit and violate SQLite SSoT. A finalized-message-bound response cursor is safe only while provider-resolvable; replay must preserve every provider-required tool/reasoning item, and missing opaque continuity fails/degrades explicitly rather than being reconstructed from a summary.
- The current implementation is the opposite of the desired Message SSoT: `TOOL_CALL_RESULT` messages are empty while `AgentToolCallRow.result_payload` stores the result, and provider/UI projections join both. The target moves the sole bounded result into `ToolResultMessage`, directly linked to an immutable `ToolCallMessage`; no child/index may regain a second lifecycle/result authority.
- The current `AgentRun.usage_payload` is a confirmed semantic collision: it stores step-budget/model continuation state, while provider-request payloads also store token/retry observation data. The target removes durable Harness continuation and keeps successful token usage in observability only; a transient Chatbot usage display does not become Message state.
- Current observability is rotating local logging plus OpenTelemetry export; it has no SQLite execution-log authority. Its loss, rotation, exporter outage, or delayed delivery must not change a reconstructed Thread, Message replay, or derived frontier action.
- The no-persistent-Run safety proof requires one application-root private ConversationWriter, not a persistent or resumable Tool Call claim. The packaged entry holds `SingleInstanceGuard`, but the development entry bypasses it; the implementation must move that guard to the common GUI root and keep worker bootstrap out of conversation recovery.
- The target removes generic effect-disposition state **without** requiring Agent Tool idempotency. It deliberately accepts that a process-loss discard followed by an explicit new provider sample may repeat semantic tool work. Current tool collision, cleanup, expensive-ML, and optional-SSH risks remain independent tool/domain concerns rather than conversation-recovery state.
