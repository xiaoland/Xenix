# Technical Decisions

## Current Boundary Evidence

- Static Agent tools live under `src/xenix/services/agent/tools.py`.
- Deterministic descriptive analysis lives in `src/xenix/services/analysis_profile.py`.
- Deterministic graph rendering lives in `src/xenix/services/analysis_graph.py`.
- Runtime boundaries in `docs/20-product-tdd/runtime-boundaries.md` require registered datasets, service-owned artifacts, validated tool arguments, and no arbitrary filesystem exposure.
- `tasks/native-ai-first/script-runtime-design.md` explicitly defers generic LLM-authored Python execution.
- Current provider-facing tools are JSON-schema function calls, not code execution requests.
- Harness contextual exposure already rejects tools that were not available for the request, so a lambda runtime would need the same exposure and validation discipline.

## Candidate Contract

The runtime should be function-shaped:

```python
def analyze(ctx, inputs, params):
    ...
    return {
        "markdown": "...",
        "metrics": {},
        "tables": {},
        "warnings": [],
    }
```

`ctx` is the only privileged gateway. It can expose methods such as:

- `ctx.load_dataset(alias)`
- `ctx.emit_table(name, dataframe, max_rows=...)`
- `ctx.artifact.create(...)`
- `ctx.warn(message)`

The Agent should not receive local paths or raw storage handles.

The tool result envelope should expose the returned dictionary as:

```text
analysis.lambda
  result.output: dict
```

The returned `dict` is the contract. It must be JSON-serializable after Xenix normalization. DataFrames, figures, paths, file handles, and other Python-native objects cannot be returned directly.

## Runtime Isolation Decision Draft

Do not claim security from Python-level sandboxing alone. In-process Python with restricted builtins is not a reliable sandbox.

MVP options:

1. Review-gated local subprocess
   - simplest product slice
   - conflicts with current MVP direction because no approval step is desired
   - service still blocks filesystem/network by API design, but OS-level isolation is limited
2. Managed worker subprocess with constrained workspace
   - better cancellation and cleanup
   - all declared outputs must be written through a manifest or IPC channel
   - still needs Windows-specific hardening if hostile code is in threat model
3. Remote/containerized analysis worker
   - strongest isolation story
   - more packaging and deployment complexity
   - likely too broad for MVP

Current decision: local subprocess first. Because MVP has no user approval, the subprocess must provide execution lifecycle control, timeout, cleanup, output capture, and cancellation. It is not a hostile-code sandbox by itself.

Threat model decision:

- in scope: accidental bad Agent code, including code that fails to compile, raises runtime exceptions, loops too long, consumes too much output budget, returns non-JSON values, creates too many artifacts, or calls unsupported context APIs
- out of scope: malicious generated code intentionally attempting process escape, arbitrary local file reads, credential access, network access, or sandbox bypass

## Operation Orchestration Compatibility

`analysis.lambda` should not replace stable operations.

Stable operations remain better for:

- common profile
- common graph
- deterministic cleaning
- SQL query/transform
- model training/application

`analysis.lambda` fills the gap where operation names and parameter schemas would become too many, too nested, or too business-specific.

## Proposed Tool Surface

Potential tool names:

- `analysis.lambda`: validate and execute a one-off function against registered datasets, returning `result.output`.

Open alternative:

- `analysis.lambda.plan` / `analysis.lambda.run` remains useful only if a future approval or reusable-analysis workflow is introduced.

Current decision from discussion: MVP does not include approval and lambdas are one-off, so a single `analysis.lambda` tool is the cleaner product surface.

Persistence decision:

- store generated code and manifest in tool-call records only
- do not create reusable lambda artifacts or named operations in MVP
- artifacts generated by the lambda may store normal artifact metadata, but not as a reusable code package

## Manifest Sketch

```json
{
  "datasets": {
    "sales": {"dataset_id": "...", "columns": ["date", "region", "revenue"]}
  },
  "params_schema": {
    "type": "object",
    "properties": {
      "min_month": {"type": "string"}
    }
  },
  "outputs": {
    "type": "dict",
    "returned_as": "result.output",
    "artifact_creation": true
  },
  "limits": {
    "timeout_seconds": 10,
    "max_output_rows": 500,
    "max_artifacts": 3
  }
}
```

## Artifact API Draft

Lambda code may create artifacts through a constrained context API. It should never write files directly and then hand Xenix a path.

Possible shape:

```python
artifact = ctx.artifact.create(
    name="revenue_trend",
    kind="image",
    content=figure_or_bytes_or_svg,
    media_type="image/svg+xml",
)

return {
    "markdown": f"![Revenue trend]({artifact.uri})",
    "artifacts": [{"id": artifact.id, "uri": artifact.uri, "kind": artifact.kind}],
}
```

The API should return artifact identity and URI, not a raw local path.

## Library Set Decision

MVP allows a broad but preinstalled analysis library set:

- `pandas`
- `numpy`
- `matplotlib.pyplot` exposed conventionally as `plt`
- `matplotlib`
- `scipy`
- `statsmodels`
- `sklearn`

Terminology decision: `matplot` in discussion means `matplotlib`, not a separate package.

Open packaging check: confirm these packages are already in the runtime/package dependency set before implementation, especially for PyInstaller distribution.

## Key Decisions Still Open

- Exact timeout, memory, row, artifact count, and output-size budgets.
- Exact lambda function signature and import style.
- Exact artifact API surface for plots: accept figure object, bytes, SVG string, or all three.

## Decisions Closed

- Library set includes pandas, numpy, matplotlib/plt, scipy, and statsmodels.
- `matplot` means `matplotlib`.
- `sklearn` is included in the lambda library set.
- Persistence stores generated code and manifest in tool-call records only.
- Threat model protects against accidental bad Agent code only, not hostile code.
- Worker location starts with local subprocess.
- Output schema accepts any JSON-serializable `dict`.
## Likely Blast Radius If Implemented

- `src/xenix/services/agent/tools.py`: new tool schema, presentation metadata, and handler.
- `src/xenix/services/agent/harness_service.py`: approval state, contextual exposure, cancellation, and turn continuation if plan/run are separate.
- New service module under `src/xenix/services/`: lambda validation, execution, output normalization, and artifact registration.
- `src/xenix/services/artifact_service.py`: likely no core change if outputs fit current artifact model, but artifact metadata may need richer provenance.
- `docs/20-product-tdd/runtime-boundaries.md`: runtime and tool boundary update after confirmation.
- `docs/30-unit-tdd/agent-harness.md`: Agent tool contract and approval behavior.
- `docs/40-deployment/runtime-state.md`: if a managed worker writes temp files or cache state.

## Verification Anchors For Future Implementation

- tool schema remains compact and provider-facing
- generated code cannot receive arbitrary local file paths
- output validation rejects undeclared files, oversized tables, and non-JSON values
- cancellation stops the worker and marks the tool result cleanly
- artifact registration uses `ArtifactService`
- thread record stores manifest, code hash, execution status, and warnings
