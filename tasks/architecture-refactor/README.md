# 项目重构

## 授权与范围

用户授权一次覆盖开发体验、可读性、架构、测试和文档的激进重构，允许约 10%–20% 的产品行为调整；该比例是容忍度，不作为必须改变行为的指标。本任务不提交 Git commit。

## 已实施的变更

- `JobScheduler` 以 domain 覆盖注册处理器，实际应用为 Knowledge 注册三个不同 kind 的处理器；改为 kind 路由、domain 共享并发，统一启动恢复与注册顺序，并用组合调度场景验证。
- `app.py` 同时负责启动界面、动态依赖表、业务装配、窗口工厂与资源释放；拆出有类型的装配和生命周期边界，消除未使用的动态依赖与重复懒加载实现。
- `data_cleaning.py` 同时承载元数据目录、DTO、文件与进程 I/O、DataFrame 执行及参数解析；按实际依赖方向拆分，使元数据与调用接口不加载执行引擎。
- 测试多处重复建立运行目录和数据库，部分成功路径之外缺少释放；引入按需的共享生命周期 fixture，并将并发测试从 sleep/轮询改为明确协调。
- 开发入口和文档保持同一事实来源；检查命令不得通过重新生成产物掩盖漂移，提供从新环境到本地验收的完整路径。

## 具体结果与行为调整

| 范围 | 结果 | 可观察的调整 |
| --- | --- | --- |
| 任务调度 | 按 `(domain, kind)` 路由，领域内共享并发与 FIFO；状态投影共用一处实现 | 三种 Knowledge 任务不再互相覆盖；跨领域同名任务互不影响；历史未调度 ML 记录不再阻塞新任务 |
| 启动与恢复 | 完整注册处理器后启动；显式装配替代动态依赖表；统一资源释放 | 禁止启动后更换处理器；域明确请求恢复时重用既有失败 JobRow；终态取消无副作用 |
| 清洗模块 | 轻量服务边界，加 contracts/catalog/engine/operations/parameters 五个职责明确的实现模块 | 27 项元数据保持相同；36 个算法/参数函数通过 AST 等价检查；源文件和操作顺序语义保持相同 |
| 测试基建 | 按需 app_paths/storage fixture、可靠 teardown、事件/屏障及调度完成条件 | 重复 pytest 调用获得不同临时目录；完整链路测试证明导入后实际可检索 |
| 开发与构建 | prepare、check、verify；相关测试入口自动准备运行资源；支持独立打包输出目录 | check 遇到过时 catalog 会明确失败，需先 prepare；旧程序占用默认输出时可选择其他构建目录 |

清洗代码合计从 1676 行降至 1242 行（减少 434 行，约 26%），不是通过删去操作实现来降低行数。对元数据哈希、分组选择、算法 AST 和构建输入的实验记录见 [evidence.json](evidence.json)。

持久化表结构未改变；ML 重启后的 orphan 语义继续由现有合同决定。调度器关闭时对活动 worker 采用统一等待预算并记录超时；这一点不承诺整个应用内所有服务都能在同一时间内退出。

仓库中其他会话更新的 `AGENTS.md` 和 `tasks/agents-rules-review.md` 保持独立，不计入本轮实现结果。
