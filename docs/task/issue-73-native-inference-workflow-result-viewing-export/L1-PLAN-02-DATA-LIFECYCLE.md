# L1 Plan 02: Data And Artifact Lifecycle

## Work-Item Contract Strategy

The work item becomes the durable contract between:

- dataset setup
- training
- inference

High-level rule:

- the selected dataset and feature columns belong to the work item at creation time
- they are no longer mutable post-creation

Implications:

- trained models on the work item share one stable feature contract
- inference no longer needs to reconstruct feature lineage from historical task payloads
- the work item becomes the anchor for both model lineage and inference input validation

## Dataset Copy Strategy

The L0 review chose to move app-managed dataset copying earlier in the lifecycle.

High-level L1 direction:

- user-selected source datasets still remain user-managed files
- when a dataset is attached during work-item creation, the app makes its managed copy then
- ML tasks consume the work-item-owned managed dataset copy instead of making their own copy at dispatch time

Why this is acceptable at L1:

- the work item is now immutable, so the managed dataset copy has a stable owner
- training and inference both benefit from resolving input data from the same stable app-owned location
- it removes repeated copying work from every ML task

Why this must stay explicit:

- this is a meaningful shift from the current branch contract that treats dataset copies as execution-scoped
- L2 must define the exact path layout and cleanup rules carefully so the new ownership remains understandable

## Inference Input Strategy

Inference should use one normalized file-based contract.

Chosen direction:

- `MLService` accepts an input-files style request shape
- batch inference passes the selected source file paths directly after validation
- manual entry is serialized by the main process into a temporary CSV file under app-owned runtime paths before task submission
- the worker process only reads normalized input files

This creates one execution contract without forcing the worker to understand UI-only row structures.

## Persisted Output Strategy

Issue `#73` needs durable local prediction output metadata, but the chosen direction is to reuse `dataset` rather than add an inference-result catalog.

High-level L1 direction:

- persisted tabular prediction outputs should be registered as `dataset` rows
- those generated dataset rows should point back to the producing inference task through nullable `dataset.ml_task_id`
- inference-specific lineage remains task-owned in `ml_task`

This gives the branch one tabular-asset concept:

- source datasets created from user-selected files
- generated datasets created from inference output files

## Dataset Reuse Guardrails

Reusing `dataset` only stays maintainable if the ownership rules remain explicit.

L1 therefore locks these rules:

- a `dataset` row still points to one concrete tabular file on disk
- `dataset.ml_task_id is NULL` means the dataset came from a user-managed source file
- `dataset.ml_task_id is not NULL` means the dataset was generated by an app-managed ML task
- model lineage, result summaries, selected trained-model id, and execution diagnostics do not move onto `dataset`
- those inference-specific details stay on the inference task and its artifacts

This keeps `dataset` as a file-registration concept rather than turning it into a full inference-report object.

## Result File Strategy

The canonical inference output should live in app-managed runtime storage under `artifacts/inference/`.

High-level rule:

- the inference worker writes result files into task-owned or inference-owned app-managed paths
- finalization registers the canonical tabular output as a generated dataset row
- open actions target the canonical file
- export actions copy from the canonical file to a user-selected destination

That split matches the reviewed user expectation without duplicating inference lineage metadata.

## Task Metadata Strategy

Inference remains an atomic `MLTask`.

The task should own:

- selected trained model id
- selected work item id
- input file list used for the run
- result summary payload
- error summary on failure
- supplementary task logs and artifacts

The dataset row should not own:

- the chosen trained model id
- the result summary
- the user-visible failure reason
- export history

Those remain task concepts.

## Migration Strategy

Issue `#73` will almost certainly require a storage migration beyond schema version `3`.

At the high level, L1 expects a migration to support at least:

- nullable `dataset.ml_task_id`
- any supporting indexes or foreign keys needed for generated dataset lookup

L1 does not require making `work_item.dataset_id` or `work_item.feature_columns` non-null at the database level.

Preferred compatibility stance:

- keep backward compatibility for existing SQLite rows
- enforce new immutability and creation rules in services and UI flow
- let L2 decide whether any optional repair path is needed for legacy incomplete work items

## Query And Listing Strategy

Reusing `dataset` should not make normal dataset selection confusing.

High-level rule:

- dataset service and UI contexts should be able to distinguish:
  - source datasets
  - generated datasets

Preferred product behavior:

- dataset setup and work-item creation flows focus on source datasets
- inference history and result views surface generated datasets
- generated inference datasets remain available for future chaining, but they should not pollute every picker by default

L2 can decide whether this distinction is API-driven, UI-driven, or both.
